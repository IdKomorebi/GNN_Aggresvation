# DNN_Aggresvation92 日志

## 0. 为什么做本号

用户对“从不同集合的完整微调轨迹中学习一个低维更新空间”持怀疑态度，因为66号已经
试过小型 FiLM adapter，后续也多次讨论过 LoRA。本号不把低维假设当成结论，而是按
“先证伪”设计实验，回答三个彼此不同的问题：

1. **表示上装不装得下**：未见集合自己的 K25 参数更新，投影到仅由训练集合学习的
   低维空间后，能否保留 K25 功能？
2. **查询时找不找得到**：只计算当前集合的一次梯度，能否预测正确的低维更新系数？
3. **真正的 LoRA 有没有用**：标准低秩权重更新在 K=1/5/25 下，是否比全参微调形成
   更好的精度—成本前沿？

三个问题不能混为一谈。“参数向量能被 PCA 压缩”不等于“预测功能能恢复”，也不等于
“查询时能从一次梯度推断出正确系数”。

---

## 1. 先澄清：以前测过的不是本号的两个方法

66号的负结果是 **FiLM adapter**：

- mask-only hypernetwork 生成每层缩放和平移；
- 只更新约1.5k个调制参数；
- K200 MAE 仍约0.059，明显落后于全参微调约0.026。

它能证明“小 adapter 不会自动成功”，但没有测试：

- 从真实 K25 任务更新中学习 PCA/SVD 方向；
- 对每个 Linear 权重训练标准 `B @ A` LoRA；
- 用当前集合真实梯度而不是仅凭 mask 选择更新。

所以本号仍需做，但必须把66号作为强负面对照背景。

---

## 2. 数据、真值和防泄漏设计

### 2.1 数据和 Oracle

- 复用69号 `MLPOracle` seed0，参数量 **157,452**；
- 输入仍为 `[x⊙m, m]`，没有另训一个替代 Oracle；
- 训练集4,589行，测试集1,967行，切分 seed=42；
- 真值是69号汇总的**逐集合专用 DNN 重训练 R²**，12个 confidential 分别评价。

### 2.2 任务设计

共收集 **865个不同集合**的轨迹：

- 子空间训练：384个；
  - 200个字段对；
  - 160个三元组（top/random各80）；
  - 24个4阶以上宽集合。
- validation目标：78个；
- audit目标：120个；
  - 50个字段对；
  - 60个三元组（top/random各30）；
  - 10个宽集合。
- 其余是计算二/三阶不可约增量所需的单字段、字段对父集。

关键防泄漏约束：

- audit/validation目标集合不进入子空间训练；
- audit/validation三元组的**所有二元父集**也不进入子空间训练；
- 所有单字段都不进入子空间训练；
- rank、ridge、步长和 LoRA 学习率只由 validation 选择；
- audit 最后只打开一次。

`outputs/validation_report.json` 已通过全部检查；新 K0 与69号5,772个逐项结果的最大误差
为 `1.1e-16`。

---

## 3. 方法

### 3.1 K25 微调轨迹

每个集合从同一个通用 Oracle 出发，固定 mask，使用与79号一致的：

- Adam；
- lr=1e-3；
- weight decay=5e-4；
- batch=256；
- 相同 mini-batch 顺序；
- 保存 K=0/1/5/25 的逐 confidential R²。

同时保存：

\[
\Delta\theta_S=\theta^{K25}_S-\theta_0
\]

以及用固定256行、1024行训练数据计算的稳定一次梯度。

### 3.2 从训练任务学习全局低维空间

把384个训练任务的 `Δθ` 堆叠后做**不中心化 SVD**：

\[
\Delta\theta_S\approx U_r a_S
\]

不中心化是必要的：adapter必须经过原 Oracle 的 `Δθ=0`，不能偷偷给所有集合加一个
平均偏移。

测试 rank：

`4 / 8 / 16 / 32 / 64 / 128 / 192 / 256 / 320`。

### 3.3 三类低维评价

1. `projected_teacher`：
   使用 audit 集合自己的真实 K25 更新求系数
   `a=UᵀΔθ`。这是**不可部署的作弊上限**，只判断子空间够不够。
2. `scalar_grad`：
   一次梯度投影后乘一个从训练任务学习的全局步长。
3. `gradmap / gradmask`：
   用训练任务学习“梯度投影→K25系数”的 ridge 映射；`gradmask` 额外输入mask。
   分别测试256行和1024行一次梯度。

### 3.4 标准 LoRA 对照

对 Oracle 的全部 Linear 层使用：

\[
W_S=W_0+B_SA_S
\]

- rank=4/16；
- K=1/5/25；
- lr=`1e-3 / 5e-3 / 1e-2`；
- K1另补扫 `0.02 / 0.05 / 0.1 / 0.2`；
- base Oracle完全冻结；
- validation选择最终配置。

这是逐集合 LoRA，仍使用当前集合训练数据；它测试的是“限制更新形状是否有利”，不是
零成本前向。

## 4. 结果一：参数能量看起来低维，但未见任务很快饱和

| rank | 训练任务更新能量 | 未见任务更新能量 |
|---:|---:|---:|
| 4 | 72.1% | 73.8% |
| 16 | 80.4% | 80.2% |
| 32 | 85.5% | 84.3% |
| 64 | 90.0% | 86.9% |
| 128 | 94.1% | 88.4% |
| 192 | 96.4% | 89.0% |
| 256 | 98.0% | 89.4% |
| 320 | **99.2%** | **89.7%** |

表面上前几个方向解释很多能量，但真正重要的是：

- 训练任务随rank继续逼近100%；
- 未见任务到128维后基本饱和在89%左右；
- rank从128增到320，只增加约1.3个百分点。

这说明剩余约10%的更新不是普通噪声，而是**新集合专属方向**。增加训练任务内部rank只会
越来越精确地记住训练任务，不能迁移到新集合。

---

## 5. 结果二：连“作弊投影上限”都恢复不了 K25

以下全部是独立 audit，直接敏感度按120个目标集合×12 confidential统计：

| 方法 | `v(S)` MAE | bias | Spearman | 三阶协同 MAE | 三阶 Spearman |
|---|---:|---:|---:|---:|---:|
| Oracle K0 | 0.0823 | -0.0822 | 0.9348 | 0.0322 | 0.3799 |
| 全参 K1 | 0.0811 | -0.0810 | 0.9347 | 0.0296 | 0.4662 |
| 全参 K5 | 0.0689 | -0.0688 | 0.9491 | 0.0260 | 0.4929 |
| **全参 K25** | **0.0477** | -0.0475 | 0.9704 | **0.0206** | **0.6877** |
| 作弊投影 rank32 | 0.0732 | -0.0730 | 0.9422 | 0.0308 | 0.3834 |
| 作弊投影 rank128 | 0.0630 | -0.0629 | 0.9524 | 0.0273 | 0.4925 |
| 作弊投影 rank320 | 0.0606 | -0.0604 | 0.9557 | 0.0266 | 0.5204 |

`projected_teacher`已经知道 audit 集合自己的 K25 参数变化，只是强行把它压进训练任务
子空间。即便用到320维：

- 直接MAE仍比全参K25差27%；
- 三阶协同MAE仍比全参K25差29%；
- 三阶排序0.520，远低于0.688；
- 三阶协同甚至略差于普通全参K5。

所以失败首先发生在“共享低维表示是否存在”这一层，还没轮到讨论如何预测系数。

---

## 6. 结果三：一次梯度映射只适合粗略 `v`，不解决协同

validation选择：

- 直接 `v`：`gradmask_1024, rank192`；
- 三阶协同：`gradmask_1024, rank320`。

独立 audit：

| 选择目标 | `v` MAE | 三阶MAE | 三阶Spearman | 单集合中位耗时 |
|---|---:|---:|---:|---:|
| 一次梯度，为 `v` 选择 | 0.0699 | 0.0298 | 0.4548 | ~2.48 ms |
| 一次梯度，为 syn3 选择 | 0.0731 | 0.0283 | 0.4518 | ~2.48 ms |
| 全参 K5 | 0.0689 | 0.0260 | 0.4929 | 12.73 ms |
| 全参 K25 | 0.0477 | 0.0206 | 0.6877 | 54.87 ms |

积极的一面：

- 一次梯度在直接敏感度上接近K5；
- 耗时约为K5的1/5。

但对本项目真正关心的不可约增量：

- 三阶MAE只略好于K0；
- 比K5明显差；
- 排序没有恢复；
- 用1024行而不是256行没有改变结论。

更严重的是任意size泛化失败：为直接 `v` 选择的一次梯度模型在10个宽集合上
MAE=**0.1394**，反而比K0的0.1001更差。它的总体0.0699主要由大量二元/三元任务贡献，
不能写成“任意大小集合都接近K5”。

---

## 7. 分size子空间能不能救？

为排除“384个训练任务里低阶太多”的混淆，分别从200个pair、160个triple、24个wide
训练集合学习子空间，只检查未见同类目标的更新能量。

| 组别 | rank | 全局空间 | 同size空间 | 改善 |
|---|---:|---:|---:|---:|
| pair | 16 | 82.4% | 83.3% | +0.9% |
| triple | 16 | 76.9% | 77.6% | +0.7% |
| wide | 4 | 41.1% | 54.0% | +12.9% |
| wide | 最大可学rank24 | — | **59.9%** | — |

- pair/triple只改善不到1%，高rank反而略差；
- wide低rank确有改善，说明size差异存在；
- 但24个wide训练任务提供的完整空间在未见wide上也只能解释59.9%，迁移更差。

因此“按size建多个子空间”不能解决本质问题，只会变成更多小专家，并重复之前band expert
的路线。

## 8. 结果四：LoRA不是没用，但作用和原设想不同

### 8.1 validation选出的最佳配置

直接敏感度和三阶协同都选择：

`rank16, lr=5e-3, K25`。

| 方法 | `v` MAE | `v` Spearman | 二阶MAE | 二阶Spearman | 三阶MAE | 三阶Spearman |
|---|---:|---:|---:|---:|---:|---:|
| 全参 K25 | 0.0477 | 0.9704 | **0.0125** | 0.8420 | 0.0206 | 0.6877 |
| **LoRA r16 K25** | **0.0432** | **0.9814** | 0.0133 | **0.8568** | **0.0185** | **0.7560** |

这是明确正结果：

- LoRA K25 的直接MAE比全参K25低约9.4%；
- 三阶MAE低约10.4%；
- 三阶排序从0.688升到0.756；
- 最大conf三阶排序从0.649升到0.724。

尤其在原本最难的 `triple_top`：

- 全参K25直接MAE=0.0845；
- LoRA K25=**0.0621**。

这更像**限制更新自由度带来的正则化**：25步时全参模型容易沿当前少量batch产生无关漂移，
LoRA只允许结构化低秩变化，反而更稳定。

### 8.2 但 LoRA 没有解决搜索成本

| 方法 | 单集合中位耗时 |
|---|---:|
| K0前向 | 0.324 ms |
| 全参 K1 | 2.92 ms |
| LoRA r16 K1 | 3.73 ms |
| 全参 K5 | 12.73 ms |
| 全参 K25 | 54.87 ms |
| LoRA r16 K25 | 63.98 ms |

当前朴素实现每次前向都形成 `B@A`，所以 LoRA K25 不但没有更快，还比全参K25慢约17%。
优化实现可能减少常数，但**25次前向/反向不会消失**。LoRA减少的是可训练参数和过拟合，
不是主要计算图。

### 8.3 一步 LoRA

validation分别选择：

- 直接 `v`：rank16, lr=5e-3；
- 三阶：rank16, lr=1e-2。

| 方法 | `v` MAE | 三阶MAE | 三阶Spearman |
|---|---:|---:|---:|
| 全参 K1 | 0.0811 | 0.0296 | 0.4662 |
| LoRA K1（为v选择） | **0.0733** | 0.0286 | 0.4781 |
| LoRA K1（为syn3选择） | 0.0761 | **0.0282** | **0.5008** |
| 全参 K5 | 0.0689 | 0.0260 | 0.4929 |

一步LoRA确实比全参K1好，但还不能稳定达到K5，更不能接近K25。高学习率0.05以上迅速
崩溃，说明不能靠“把一步走大”模拟多步。

## 9. 关于三阶召回率的口径

audit有60个三元组，其中32个真值 `max_conf syn3>0.10`。Top30%候选池只有18个位置，
所以召回率理论上限就是：

\[
18/32=56.25\%
\]

LoRA K25和全参K25都达到56.25%，代表18个位置全部命中强集合（precision=100%），不是
“还漏了将近一半所以方法很差”。这个设计下召回已饱和，区分方法应主要看：

- per-conf协同MAE；
- 全体协同Spearman；
- max-conf排序；
- 不同候选池大小的完整recall-cost曲线。

`syn3>0.20` 在本audit只有1个，任何该档召回数字都没有统计意义。

## 10. 最终结论

### 10.1 否定的假设

**“从已有集合K25轨迹学习一个全局低维更新空间，再用一次梯度恢复任意集合的K25响应”**
没有通过。

原因不是实现少测了几个rank：

1. rank320在训练轨迹已解释99.2%；
2. 未见任务仍停在89.7%；
3. 使用审计任务真实系数的作弊上限仍明显落后K25；
4. 分size子空间不能救pair/triple，wide迁移更弱；
5. 一次梯度只能做到直接 `v` 近似K5，协同仍近似K1。

因此不建议把 PCA/SVD 轨迹子空间写成论文主方法，也不建议继续堆更高rank或更多
size expert。

### 10.2 保留的正结果

**LoRA K25 应保留为最终少量候选的高质量攻击者/认证器。**

它：

- 没有取代通用 Oracle；
- 没有建立poly2式第二预测模型；
- 在独立audit上比全参K25更准；
- 对最难三元组和三阶协同提升尤其明显。

但它不适合给成千上万候选全部跑K25，不能承担廉价全扫。

### 10.3 下一条更合理的研究路线

92号给出的新证据指向的不是“继续压缩 K25 的最终参数变化”，而是：

> 保留 Oracle，并把 **一步 LoRA 本身元训练成专门恢复父子不可约增量的适配器**。

具体形式：

1. base Oracle固定，避免重演65号Reptile破坏K0；
2. 只在多层放rank16 LoRA；
3. 训练episode同时采样 child `S` 和全部直接 parents；
4. inner loop只做**一步** LoRA；
5. outer loss同时优化 child/parent预测和
   `v(S)-max v(parent)`；
6. 学习 LoRA 的初始A、分层学习率和梯度预条件，而不是事后对 K25 参数做线性PCA。

这条线有两个实际依据：

- 本号一步LoRA已经稳定优于全参K1，说明“一步可学适配器”并非零信号；
- LoRA K25优于全参K25，说明低秩约束对困难协同确有正确归纳偏置。

它仍不能保证成功，但比全局轨迹PCA更贴近真正目标，也比重做独立poly2模型更统一。

## 11. 诚实边界

- Oracle、完整微调和 LoRA 各使用一个模型种子；本号优先扫方法/rank/lr，没有重复三种子。
- 论文声称 LoRA K25 优于全参K25前，应对最佳配置补第二模型种子和第二任务切分。
- LoRA耗时是当前直接实现，不是专用融合kernel；绝对毫秒可能优化，步数结论不会改变。
- 本号只在二/三阶及少量宽集合验证，因为目的正是先判断是否值得向更高阶扩展。
- audit三元组一半来自旧候选、一半随机，不代表全13,244个三元组的自然强度比例。
