# DNN_Aggresvation66 日志

## Modify by Claude: 2026-07-13

## 1. 子项目定位（元学习改进赌注：从"共享初始化"换成"掩码条件化参数生成"）

65 号 Reptile（优化式元学习：共享初始化 + K 步微调）四配置全败，诊断为
"子集任务最优解在参数空间太发散，不存在一个对所有子集 K 步可达的初始化"。
用户查到的相关工作（HetMAML CIKM'21、M3S AACL'22、ICCV'23 模态缺失元学习、
MetaFS、TPAMI'24 参数高效模态适配）指向另一条改进路线：**表示式元学习**——
不找万能起点，而是学一个映射 m→θ*(m)：hypernetwork 以掩码为任务描述子，
直接生成该子集的专属参数（FiLM 调制），借鉴 MetaFS 的参数生成器思想；
查询时还可只微调生成的 ~1.5k 个 FiLM 参数（借鉴 TPAMI'24 的 <1% 参数适配）。

预注册假设：
- H1：hypernet 生成参数的 K0 保真度 < 63 号输入拼接式 MLP oracle 的 0.089；
- H2：只调 FiLM adapter 可用大 lr 快速精修且不崩（对照 64 号全参大 lr 崩溃）。

## 2. 方法

`src/hyper_oracle.py`：backbone 与 63 号 MLPOracle 同容量（2nG→256×3→nC）；
hypernet: m→128→每隐藏层 (γ,β)，FiLM 施加在 ReLU 后，最后一层零初始化（起点恒等）。
训练协议与 63 号完全对齐（同掩码分布/预算/内部验证/种子口径），`scripts/train_hyper.py`。
评测 `scripts/eval_hyper.py`：60 号 50 个真值子集，K0 + 三个微调臂。

## 3. 结果（负结果：两个假设都未通过）

训练：满输入 R²=0.843（与 63 oracle 同量级）。mean|v̂(K)−truth|（50 子集 ×2 种子）：

| K | 0 | 5 | 10 | 50 | 200 |
|---|---:|---:|---:|---:|---:|
| film adapter, lr 1e-2 | 0.0916 | 0.0871 | 0.0821 | 0.0685 | 0.0591 |
| film adapter, lr 1e-3 | 0.0916 | 0.0869 | 0.0855 | 0.0798 | 0.0721 |
| 全参微调, lr 1e-3 | 0.0916 | 0.0899 | 0.0722 | 0.0441 | 0.0262 |

- **H1 ❌**：hyper K0=0.0916 vs 63 MLP oracle 0.089——掩码条件化从"输入拼接"升级为
  "FiLM 参数生成"没有带来任何保真度提升；
- **H2 半❌**：film adapter 大 lr 确实不崩（PEFT 稳定性成立），但改善缓慢且 plateau 在
  ~0.059，远差于全参微调；只动 1.5k 个调制参数不足以承载子集特化所需的容量；
- 全参微调轨迹（0.0722@K10→0.0262@K200）与 64 号从 63 oracle 的 naive 暖启动
  （0.071@K10→0.030@K200）**几乎重合**——hypernet 条件化对微调起点质量也无贡献。

## 4. 三连负的共同根因（63 GNN / 65 Reptile / 66 hypernet）

三个"模型/训练技巧"赌注在同一根因上失败：**输入拼接式随机掩码 MLP oracle 在本数据上
已经坐在摊销的天花板上**。到真值的残余差距（~0.08）来自"每个子集需要专属容量特化"，
只有真实的逐子集优化（数百步微调或重训）能闭合；不存在结构先验（GNN）、初始化
（Reptile）或条件化机制（hypernet）能绕过它的捷径。这与 PJM RTO 聚合数据字段耦合
高度集中（负荷预测枢纽主导）有关，任务间共享结构已被联合训练全部吃掉。

## 5. 结论

方法创新不再押模型/训练技巧（三赌注全空，且根因一致——这本身是论文中有价值的
消融/边界章节素材）。可辩护的贡献回到：问题形式化（v_c(S) 集合函数 + 56 号协同证明
单点不适定）+ 忠实测量方法学（58 置零伪影 / 60 噪声底 / 63 摊销低估量化 / 64 暖启动
10-15× 提速作为工程组件）+ 应用（协同图、最小防护集，待做）。
